### 1. 全部已读后刷新红点回弹修复（2026-09-05）

- **问题**：点"全部已读"后刷新，铃铛红点重新出现 25 条未读

- **根因**：`NotificationScheduler.insertIfNotExists()` 的去重查询带 `is_read=0` 条件。
  用户标记已读后记录变 `is_read=1`，定时任务（每 2 分钟）扫描时查不到未读记录，
  就重新插入一条新的未读通知 → 红点反复出现

- **修复**：去重查询去掉 `.eq("is_read", 0)`，改为只要 `(receiver_id, source_type, source_id)`
  存在过任意通知（含已读）就跳过，不再重复生成

- **影响文件**：`backend/src/main/java/com/erp/scheduler/NotificationScheduler.java`
  （`insertIfNotExists` 方法）

- **验收**：标记全部已读后，经过两轮定时任务扫描，未读数保持 0，无新通知插入

### 3. 待审批通知与「我的待办」口径统一（2026-09-14）

- **问题**：设置中心配好销售订单审批（审批人=李工）后，小铃铛有红点，但设置中心「我的待办」/
  工作台「待我审批」看不到刚提交的单。

- **根因（两条链路口径不一致，本地 erp\_db 实测）**：

  1. 铃铛红点由 `NotificationScheduler` 每 2 分钟扫描生成，其 `inferRoles()` 是**按 username 关键字猜角色**
     （含 sale/purchase/warehouse... 才判对应角色，猜不出就默认 ADMIN）。`lyc123` 猜不出 → 判为 ADMIN
     → `getMyPendingApprovals` 返回模块维度全部「待审核」销售订单 → **16 个账号**都收到
     「待审批：销售订单 SO-20260914-0005」假通知。
  2. 工作台/「我的待办」用**真实角色**（`AuthInterceptor`：sys\_user\_role → sys\_role.role\_code，李工=SALES）

     - 审批引擎真实指派匹配 → 页面为空。两处口径不一致 = 用户看到的「红点有、页面空」。

- **修复**：

  - `NotificationScheduler.inferRoles()` → `loadRealRoles()`：查 `sys_user_role` + `sys_role.role_code`
    （无角色降级 VIEWER），与登录鉴权口径完全一致；

  - 「待审批」通知改用 `dashboardService.getMyEnginePendingApprovals(username)`
    （只推**审批引擎真实指派给该用户**的待办），与「我的待办」页面同源，不再用模块维度列表广播；

  - `SysNotificationService` 两处 `setSourceType` 统一为**小写**：原来引擎通知写大写 `SALE_ORDER`、
    定时任务写小写 `sale_order`，同一单据会被 `uk_sys_notification_unread_source`
    去重索引判为两条 → 铃铛重复红点（本地已实测复现：同一测试单先出现引擎通知，
    下一轮扫描又插入一条定时任务通知）。

- **影响文件**：

  - 改 `backend/src/main/java/com/erp/scheduler/NotificationScheduler.java`

  - 改 `backend/src/main/java/com/erp/notification/service/SysNotificationService.java`

### 3. 通知去重维度补上「通知类型」（2026-09-14）
- **问题（实测事故）**：唯一索引与 Java 预查重口径都是 `receiver_id + source_type + source_id + 未读`，**不含 type**
  → 同一张单的**不同类别提醒互相顶掉**。实锤：销售订单 `SO-20260914-0005`（内部 id=258）在草稿阶段先写入
  「草稿待提交」（type=draft）未读通知，随后提交审批时「待审批」（type=approval）通知被判定为重复 →
  **静默跳过** → 小铃铛里始终没有待审批提醒、语音播报也就没有数据可播。
- **修复**：预查重条件 + 唯一索引均加入 `type`（`receiver_id + type + source_type + source_id + 未读` 才算重复），
  不同类别提醒可各自存在；新建 `db/76_notification_dedup_include_type.sql` 并登记 `deploy-kit-manifest.txt`。
  新索引比旧索引**更宽松**，存量数据天然满足、无需清洗；索引名保持不变避免其它引用失效。
- **同批调整**：按用户要求**关闭「草稿提醒」**（`notification.type.draft.enabled=false`）并清理 548 条历史草稿通知
  （清理前已备份到 `bak_20260914_draft_notification`）。

## 二、系统架构说明

### 通知来源（两套独立系统）

1. **sys\_notification**（小铃铛）：`/api/notifications/*`

   - 由 `NotificationScheduler` 每 2 分钟扫描生成（草稿/审批/超期/应收应付）

   - 也由 `notifyApprovalTask` / `notifyApprovalFinish` 事件驱动生成
2. **approval\_notification**（审批通知页）：`/api/approval/notifications/*`

   - 审批流转时写入，独立于小铃铛

### 去重机制

- 唯一索引 `uk_sys_notification_unread_source`：`(receiver_id, source_type, source_id) WHERE is_read=0`
  → 同一来源的未读通知唯一

- `insertIfNotExists` 应用层去重：同来源有通知就跳过（修复后不区分已读未读）

## 四、踩坑记录（不再犯）

1. **定时任务去重要带"已读"语义**：去重查询不能只查未读，否则用户标记已读后定时任务会重复生成
2. **通知是事件提醒不是轮询弹窗**：同一 source 只提醒一次，用户已读后不重复打扰；
   用户主动清空已读（物理删除）后才会再次提醒
3. **语音播报的增量基线必须取「后端返回值」，不能用前端本地值**：铃铛点击通知会先本地 `-1`，
   若拿本地值当基线，下一轮轮询拿到后端旧值会被误判为"新增"→ 同一批通知反复播报。
   正解：单独保存"上次后端返回的 approval 未读数"作基线，且**首次拿到的值只建基线、不播报**（避免每次刷新页面都响）。
4. **定时任务里禁止按 username 猜角色**：`NotificationScheduler` 原先用 `inferRoles()`（username 含
   sale/purchase/... 才算对应角色，否则默认 ADMIN），与 `AuthInterceptor` 的真实角色口径不一致，
   会把不属于该用户的待审批推给全系统（本次 16 个账号）。**凡需要角色的后台任务，一律查
   `sys_user_role`** **+** **`sys_role.role_code`**。
5. **同一来源通知必须共用一套 source\_type 大小写**：引擎事件通知写 `SALE_ORDER`（大写）、
   定时任务写 `sale_order`（小写），`uk_sys_notification_unread_source` 按三元组去重会判成两条 →
   铃铛重复红点。现统一为小写。
6. **语音提醒不能依赖 AI 小助手组件的生命周期**：小助手在设置中心页被 `v-if="!isSettingsPage"` 卸载，
   把播报逻辑写进该组件会"一到设置中心就哑了"→ 播报放 `frontend/src/utils/voiceNotify.js`，
   由 MainLayout 挂载时初始化一次；组件只负责浮球气泡与静音按钮的呈现。
