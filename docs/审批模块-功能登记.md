# 审批模块 功能/修复登记

> 审批引擎 = 流程定义（`approval_flow` / `approval_node` / `approval_node_approver` / `approval_condition`）
> + 运行时任务（`approval_task` / `approval_log` / `approval_notification`）
> + 单据级审批开关（`sys_config`）+ 待办页 + 小铃铛通知。
> 入口：设置中心 → 审批设置 →（审批开关 / 审批流程 / 我的待办 / 审批通知）；工作台 → 待我审批。

## 一、已完成

### 1. 审批引擎基础能力（2026-08 前建成，长期在用）
- **开关**：全局 `approval.enabled` + 单据级 `approval.bill.<billType>.enabled`（设置中心 → 审批开关）。
  关闭审批时「提交」直接置「已生效」并触发生效逻辑。
- **流程定义**：流程（编码/名称/单据类型/启用/优先级 priority/触发条件 conditionExpr）；
  节点（名称/序号/审批人模式 `single|any|sequence|auto`）；节点候选审批人（员工/账号，多人可搜索选择）；
  条件模板（独立入口维护，按 targetNodeOrder 关联节点，不随流程保存被删）。
- **条件路由**：`conditionExpr` 新格式 `{"rules":[{"field","op","value"}]}`（AND 关系，op 支持
  eq/ne/contains/gt/ge/lt/le，字段含表头字段与自定义字段）；老格式
  `{"payment_category":..,"min_amount":..}` 兼容保留。多流程按 `priority` 命中，无条件流程兜底。
- **运行时流转**：提交 → `startApproval` 生成首节点待办 → 通过 / 驳回 / 转交 / 候选人选审批人
  → 流程终结经 `BillApprovalCallback` 回写单据状态（已生效/驳回草稿）并触发业务影响。
- **待办与通知**：设置中心「我的待办」`/api/approval/tasks/my-pending`；「审批通知」
  `approval_notification`；小铃铛 `sys_notification`（引擎事件 + 定时扫描两路来源）。
- **抄送**：流程 `notifyUserIds`，审批结束推送给发起人 + 抄送人（`notifyApprovalFinish`）。

  - **提交时校验**「节点审批人必须能解析到启用账号」，否则抛业务异常并在提示里指明流程/节点/审批人；

## 二、关键机制（改代码前必读）
- **状态机**：草稿 → 待审核 → 已生效；驳回 → 草稿。免审批时提交即「已生效」。
- **身份口径**：登录用户名 ↔ 审批人姓名，统一由 `ApprovalRuntimeService.resolveDisplayName`
  解析（sys_user → employee.employee_name → real_name → username 兜底）。
- **选流顺序**：`priority asc, flow_id asc`（2026-09-14 加固，此前顺序不稳定）。
- **待办过滤**：`getMyPendingTasks(username)` 按 `current_approver` / `assignee_ids` 精确匹配解析后的姓名。

## 四、踩坑记录（不再犯）
1. **同优先级多流程不能依赖数据库默认返回顺序**：必须给排序加唯一 tie-breaker（flow_id）。
2. **同一单据类型只允许一条无条件兜底流程**：多条并存 = 选流取决于排序 = 单据随机进错流程。
3. **审批人必须能解析到启用账号**，否则生成的待办对所有人不可见、单据永久卡死。
   `?` 乱码要先用 `convert_to(col,'UTF8')` 确认是真乱码还是查询客户端乱码。
4. **后台任务取角色禁止猜**：一律查 `sys_user_role` + `sys_role.role_code`，与登录鉴权同源。
5. **含 DELETE/UPDATE 的数据清理脚本不进 `deploy-kit-manifest.txt`**（铁律只增不改不删），
   客户库同款脏数据须人工确认后单独执行。
