# 单据状态机制统一改造设计（草稿→提交→审核/驳回→反审批→结案/反结案→作废/反作废）

> 版本：v1.0  
> 日期：2026-08-15  
> 适用范围：系统内全部带审批流程的单据编辑页 / 列表页 + 后端对应 Service / Controller

---

## 1. 背景与目标

此前系统的单据状态存在以下问题：
1. 「保存」和「提交审批」按钮语义混淆，用户不清楚为什么要先「保存」再点「提交审批」；
2. 草稿保存时会触发必填校验，导致"还没填完就先存为草稿"的场景无法使用；
3. 状态机没有统一的「反审批 / 结案 / 反结案 / 作废 / 反作废」标准；
4. 不同模块（Sale/Purchase/Subcontract/Inventory/Finance/Production）的状态体系不统一：
   - 部分模块（Subcontract、SaleOrder、PurchaseOrder）有"数字状态枚举 + closeStatus"双字段；
   - 其他模块（采购申请、采购入库、销售发货…）只有字符串 status；
5. 部分模块"已审核态仍可直接修改字段"、部分模块不可，没有统一规则；
6. 缺少"作废"作为严格型（按金蝶/用友）的终态校验与下游影响释放。

**本设计目标：** 按照金蝶 K3 WISE / 用友 U8 的业界通用标准，为所有单据统一一套完整状态机 + 按钮命名 + 后端校验规则 + 前端编辑性控制，并补充"草稿宽松保存、提交严格校验、作废严格型下游校验、结案/作废双终态、反操作"。

## 2. 用户已确认的关键决策

| 决策项 | 结论 |
|---|---|
| 终态定义 | **双终态**：{已结案, 已作废}，两者均为"完结"——不可修改/编辑/删除/提交/再结案或再作废，仅允许各自的反向操作（反结案 / 反作废） |
| 审批通过后是否可直接修改字段？ | **不可直接修改**。必须先点「反审批」退回到草稿，再编辑、再「提交」重新走审批。（避免后续变更不留痕） |
| 保存与提交的拆分 | 「保存」= 存草稿（草稿态宽松保存，不校验必填）；「提交」= 草稿→待审核，直接进入审批流程（无需用户先点保存，提交时做完整校验） |
| 草稿保存校验 | **草稿保存不校验必填 / 业务逻辑**，哪怕核心字段为空都允许落库；仅在「提交」「审核」两个动作时做严格校验 |
| 作废规则 | 选 **A 严格型（金蝶/用友标准）**：作废前校验无下游已生效单据，有则报错"请先作废下游单据 XXX、XXX"；作废后释放库存占用 / MRP 需求 / 应收应付挂账；选单/拉单过滤掉已作废单据；保留单号与数据用于审计；**提供反作废**，恢复到作废前原状态 |
| 与金蝶/用友的一致性 | 按金蝶 K3 WISE / 用友 U8 业界通用标准设计 |

## 3. 状态机

### 3.1 统一状态枚举（双字段方案 = 金蝶/用友标准）

每个业务单据同时维护两个独立字段：

| 字段 | 含义 | 取值 |
|---|---|---|
| `status` | **主业务状态**（审核流程态） | 0 = 草稿 / 1 = 待审核 / 2 = 已审核 / 7 = 已作废（字符串体系沿用中文字符串枚举的兼容映射见 3.3） |
| `close_status`（或命名为 `closed_flag`） | **结案标志**（独立的完结标志，与 status 分开，金蝶/用友标准） | 0 = 未结案 / 1 = 已结案 |

⚠️ 历史兼容：
- Subcontract 系列与 SaleOrder / PurchaseOrder 等原本已有 `closeStatus` 或数字枚举的模块保持原含义并升级对齐；
- 原本仅字符串 status（如采购入库、销售发货等）的模块新增 `close_status` 字段（默认 0），`status` 的字符串与数字枚举做映射（见 3.3）。

### 3.2 状态流转图

```
                 ┌──────────────────────────────────────┐
                 │                                      │
                 ▼                                      │
   ┌──────┐  保存 ┌──────┐   提交  ┌────────┐   审核  ┌────────┐  结案  ┌────────┐
   │ 新建 │──────►│草稿(0)│────────►│待审核(1)│────────►│已审核(2)│────────►│已结案(1)│
   └──────┘       └──────┘         └────────┘         └────────┘        └───┬────┘
                  ▲ ▲  │              │                 │  │                │
                  │ │  │              │驳回             │  │作废            │反结案
                  │ │  │              ▼                 │  ▼                │
                  │ │  │          ┌──────┐             │  ┌────────┐       │
                  │ │  └──────────│草稿(0)│◄─反审批────┘  │已作废(7)│◄──────┘（不可对已结案作废，需先反结案）
                  │ │             └──────┘                └───┬────┘
                  │ │  反作废（若作废前为草稿）                 │
                  │ └───────────────────────────────────────────┘反作废（回到作废前原状态）
                  │
                  │ 删除（仅草稿可删除）
                  ▼
               [单据删除，无追溯]
```

**补充说明**：
- 「已审核(2)」才允许执行 **结案 / 作废 / 反审批** 三个动作之一；
- 「已作废(7)」与「已结案(close_status=1)」均不可修改 / 编辑 / 删除 / 再结案或再作废；
- 已结案的单据不能直接作废，必须先**反结案**回到已审核(2)；
- 已审核(2) 单据若要修改字段，必须先点 **反审批 → 回到草稿(0)** → 编辑 → 提交 → 重新审核；
- 「反审批」和「作废」均采用严格型下游校验：有下游已执行单据则不能反审批/不能作废，先提示并阻塞（见第 6 节）。

### 3.3 字符串状态 ↔ 数字枚举映射（兼容历史模块）

| 字符串 status | 映射数字 status | 说明 |
|---|---|---|
| `''` / `null` / `undefined` | 0 草稿 | 新建/未提交 |
| `'草稿'` | 0 草稿 | |
| `'待审核'` / `'待审批'` | 1 待审核 | |
| `'已审核'` / `'审批通过'` / `'已确认'` | 2 已审核 | |
| `'驳回'` | 0 草稿 | 回到草稿重新编辑 |
| `'已下达'` | 2' 已审核的子类（仍映射 2=允许反审批/结案/作废，有下游执行时禁止反审批） | Subcontract 专有 |
| `'执行中'` | 同上 | 按"已审核子类"处理，见 6.2 |
| `'已完工'` | 仍视为"已审核子类"，需根据下游执行情况判断反审批/作废门槛 | Production 专有 |
| `'已结案'` / `'已关闭'` | 保留字符串，但**同时将 close_status 置 1**，统一以 close_status 判终态 | |
| `'已作废'` | 7 已作废 | status=7 同时存在，以 status===7 判终态 |
| `'已取消'` | 0 草稿（或视为作废=7，按业务情况；本设计暂按作废=7处理） | |

> **改造实现**：前端 `statusText()` / `statusType()` / 条件判断统一走辅助函数 `BillStatus.toNumber(form.status)`、`BillStatus.toString(n)`；后端以 `BillStatusEnum` 统一处理，避免两套逻辑分叉。

## 4. 前端按钮统一命名 & 展示规则

### 4.1 按钮命名（按用户要求）

| 新按钮文案 | 原可能有的文案 | 说明 |
|---|---|---|
| **保存** | 保存 | 存草稿，不触发审批，不做必填/业务校验（宽松） |
| **提交** | 提交审批 / 提交流程 | 草稿(0) → 待审核(1)，完整校验必填+业务规则 |
| **审核** | 审核 / 审批通过 | 待审核(1) → 已审核(2)，完整校验业务 |
| **驳回** | 驳回 / 拒绝审批 | 待审核(1) → 草稿(0)，允许填写驳回原因 |
| **反审批** | 反审核 / 反核准 / 撤销审核 | 已审核(2) → 草稿(0)，严格校验无下游（见 6.2） |
| **结案** | 关闭 / 结案 | 已审核(2) → close_status=1，允许业务完结 |
| **反结案** | 反关闭 / 打开 / 撤销结案 | close_status=1 → close_status=0，回已审核(2) |
| **作废** | 作废 | 草稿(0)/已审核(2) → 已作废(7)，严格校验下游 + 释放影响（见 6.3） |
| **反作废** | 恢复作废 / 取消作废 | 已作废(7) → 回到作废前原状态，重新占用影响 |
| **删除** | 删除 | 仅草稿(0) 可见/可操作，已审核及以上不得删除（只能作废，保留追溯） |

### 4.3 编辑性控制（非草稿 + 终态 = 只读）

此前 `isDraft` 的语义已经不适用。新增两个计算属性，按金蝶/用友标准：

```js
// 字符串/数字统一成数字
const statusNum = computed(() => BillStatus.toNumber(form.status))

// 是否"草稿态"——允许显示【保存】【提交】【删除】按钮，并且表单可以编辑
const isDraft = computed(() => statusNum.value === 0)

// 关键字段（业务字段/单号/自定义字段/明细单元格/操作列删除/明细工具栏增删）:disabled 控制
// ✅ 草稿态：可编辑
// ❌ 其他状态（待审核/已审核/已结案/已作废）：不可编辑
// 注：已审核要改字段必须先"反审批 → 草稿 → 编辑 → 提交 → 审核"
const isEditable = computed(() => statusNum.value === 0 && !(Number(form.closeStatus) === 1))

// 是否处于"完结态"——禁用除反操作之外的所有业务按钮
const isFinalized = computed(() => Number(form.closeStatus) === 1 || statusNum.value === 7)
```

⚠️ **委外 Subcontract 5 个模块**（数字枚举）、**PurchasePrePayment / SalePreReceipt**（数字枚举）、其余字符串状态的模块，**全部统一使用上述 `BillStatus.toNumber()` 双字段判断**，不再各写各的 isStatus。

## 5. 保存 & 提交的校验拆分（核心需求点）

### 5.1 前端层

```
【保存】onSave()
  ├─ 不调 headerFormRef.validate()
  ├─ 只做"纯落库"：把当前表单内容原样传给 /save 接口
  └─ 成功后：loadDetail() 刷新单据（若新增则跳转到 /edit/:id），并提示"已保存为草稿"

【提交】onSubmit()
  ├─ 先调 await headerFormRef.validate()  ← 必填校验
  ├─ 再跑自定义业务校验（明细行非空、金额/数量一致性、交期逻辑、客商、物料是否生效等）
  ├─ 通过后：传 /submit 接口（若未保存，服务端内部也可先保存再流转）
  └─ 成功后：状态变为待审核(1)，loadDetail()，提示"已提交进入审批流程"
```

### 5.2 后端层

每个业务 Controller 区分 **两个独立接口**（金蝶/用友标准）：

| HTTP | 路径 | 入参 | 校验要求 | 状态流转 |
|---|---|---|---|---|
| POST | `/{module}/{entity}/save` | form JSON | **不校验必填，不校验业务逻辑**；只做类型转换 & 非空字符串默认 & 自定义字段落库 & `create_by/update_by` 填充 | 若 id 空 → 新建并设 status=草稿(0)；若 id 非空 → 更新但**禁止修改状态、close_status（强制忽略入参这俩字段）** |
| POST | `/{module}/{entity}/submit` | form JSON + id（可空） | **完整校验**：① headerFormRef 必填 ② 业务一致性 ③ 客商/物料有效性 ④ 若为新增还需保存一次；失败直接抛业务异常 | 草稿(0) → 待审核(1)，若已存在则必须当前是草稿 |
| POST | `/{module}/{entity}/approve` | id + 可选审批意见 | 业务校验（金额/库存/信用等） + 必须当前是待审核(1) | 待审核(1) → 已审核(2)，写审批人、审批时间 |
| POST | `/{module}/{entity}/reject` | id + 驳回原因 | 必须当前是待审核(1) | 待审核(1) → 草稿(0)，写驳回原因 |
| POST | `/{module}/{entity}/reverse-approve` | id + 可选反审原因 | **严格下游校验**（§6.2） + 必须当前是已审核(2) 子类 & close_status=0 | 已审核(2) → 草稿(0) |
| POST | `/{module}/{entity}/close`（结案） | id + 可选结案原因 | 必须当前是已审核(2) 子类 & close_status=0 | close_status=1，写结案人/时间 |
| POST | `/{module}/{entity}/reopen`（反结案） | id | 必须 close_status=1 | close_status=0 |
| POST | `/{module}/{entity}/void`（作废） | id + 可选作废原因 | **严格下游校验 + 释放影响**（§6.3） | status → 7（已作废），并在 `bill_before_status` 列记录作废前 status，close_status 保持不变（已结案不可作废） |
| POST | `/{module}/{entity}/unvoid`（反作废） | id | 必须 status=7 | status=bill_before_status，重新占用影响 |
| DELETE | `/{module}/{entity}/{id}` | id | 必须 status=草稿(0) & close_status=0 | 物理或逻辑删除（按模块保留） |

> ⚠️ 注：历史存在 `cancel`（取消单据）接口。本设计中 `取消=作废` 语义，保留原接口但内部改为走 `/void` 同一条实现，避免重复入口。

## 6. 反审批 / 作废 的严格下游校验 & 影响释放（金蝶/用友标准）

### 6.1 单据"上下游关系"登记

对每种单据类型登记其"上游/下游生成关系"（沿用现有选单 source-picker 的 source_type 映射即可）：

| 本单据 | 下游单据（本单存在下游时，禁止反审批/禁止作废，需先作废/删除下游） |
|---|---|
| 销售报价 SaleQuote | 销售合同 / 销售订单 |
| 销售合同 SaleContract | 销售订单 |
| 销售订单 SaleOrder | 销售出库单 SaleDelivery / 销售发票 SaleInvoice / 生产工单 WorkOrder / MRP计划 |
| 销售出库 SaleDelivery | 销售发票 SaleInvoice（已开票行） / 库存流水 |
| 销售发票 SaleInvoice | 收款核销单 / 应收凭证 |
| 采购申请 PurchaseRequest | 采购合同 / 采购订单 |
| 采购合同 PurchaseContract | 采购订单 |
| 采购订单 PurchaseOrder | 采购入库 PurchaseInbound / 采购发票 PurchaseInvoice |
| 采购入库 PurchaseInbound | 采购发票（入库数量已开的部分） / 库存流水 / 应付 |
| 采购发票 PurchaseInvoice | 付款核销单 / 应付凭证 |
| 委外订单 SubcontractOrder | 委外发料 SubcontractPick / 委外入库 SubcontractInbound / 委外补料 SubcontractSupplement / 委外退料 SubcontractReturn |
| 委外发料 SubcontractPick | 库存流水 |
| 委外入库 SubcontractInbound | 应付 / 委外发票（如有） |
| 生产工单 WorkOrder | 生产领料 / 生产入库 / 工序转移 / 报工 / 补料 / 退料 |
| 生产领料 / 入库 | 库存流水 |
| 库存调拨 / 盘点 / 出入库 Other* | 库存流水 |
| 付款凭证 PaymentVoucher / 收款凭证 PaymentReceipt | 应收应付核销 / 现金银行流水 |
| 费用报销 OperationExpense | 应付 / 付款核销 |
| BOM | 生产工单引用（有生产订单使用该BOM时，不允许反审批/作废该版本BOM） |

> （完整映射表在实施阶段按现有选单 SourcePicker + 后端推单/被推单配置补齐。）

### 6.2 反审批（reverse-approve）校验规则（严格型A）

执行反审批**前**依次执行：

1. **状态门槛**：`status` ∈ { 已审核(2) / 已下达(3) / 执行中(4) } 且 `close_status = 0`（未结案）
   - 若当前已结案：报错"请先反结案再反审批"
   - 若当前是 生产工单 `已完工(5)`：默认按"已审核子类"处理，但如果有下游入库/报工已执行，按规则2阻塞
2. **下游单据存在性校验**：按 6.1 映射表递归查询，只要存在任一"下游已经审核(2)以上 / close_status=1 / status=7（被作废也没关系，主要是有效下游）"的单据 → 报错，**列出具体单据号**：
   > "该单据存在下游已生效单据，无法反审批。请先作废/删除下游：销售出库单 SO_OUT-2026-08-0001、销售发票 SO_INV-2026-08-0003。"
3. **业务影响已发生校验**（针对未生成下游单据但业务影响已发生的情况）：
   - 销售订单：已被 MRP 运算产生了计划单且未取消 → 阻塞
   - 采购订单：已部分入库 / 已部分开票的 → 阻塞
   - 库存单据：已产生库存流水且不能被"反影响"回滚 → 阻塞
4. 校验通过 → 状态退回草稿(0)，原"审批人、审批时间、审批意见"保留字段备查（不清除，金蝶/用友标准）。

### 6.3 作废（void）校验规则 & 释放影响（严格型A）

作废前校验：
1. **不得对已结案（close_status=1）作废**——需先"反结案"
2. **不得存在下游已审核单据**（同 6.2 规则2，列出单据号）
3. **不得存在业务影响未释放（见下）**（释放也在作废事务内一起做）

作废事务（同一次提交内完成，失败回滚）：
1. `status` 写为 7（已作废），`bill_before_status` 记录作废前状态，写作废人、作废时间、作废原因；
2. **释放影响（核心）**：
   - **库存占用/预留：** 若本单据类型产生了库存预留/锁定/待发量/待收量 → 调用 `InventoryFreezeService.releaseByBill(billType, billId)` 释放；
   - **MRP 需求/供给：** 若本单据参与 MRP → 调用 `MrpService.removeBillDemandSupply(billType, billId)`，并为下次 MRP 重算打标；
   - **应收应付挂账：** 若本单据产生应收/应付（未核销的） → 调 `ArApService.cancelUnclearedByBill(billType, billId)` 取消挂账（若已核销则已属于"有下游"，在前面校验已拦截）；
   - **可用量/信用额度：** 销售订单产生的信用占用 → 释放对应客户的信用额度占用；
3. 同步审批/业务流引擎：把本单据从待处理列表中移除，不再触发下游推单/消息。

反作废（unvoid）事务：
1. 读取 `bill_before_status` → 恢复 `status = before_status`；
2. **重新占用** 6.3 中被释放的全部影响（库存/MRP/应收应付/信用），失败整体回滚；
3. 清理 `bill_before_status`（或保留历史，按审计要求）。

## 10. 验证清单（必过）

1. **草稿宽松保存**：新增任何单据，所有必填留空 → 点【保存】→ 成功提示"已保存为草稿"、单据落库、字段仍是空。
2. **提交严格校验**：同一草稿所有必填留空 → 点【提交】→ 高亮提示必填项并阻止提交。
3. **状态流转闭环**：
   - 草稿 → 提交 → 待审核 → 审核 → 已审核 → 结案 → 已结案 → 反结案 → 已审核 → 反审批 → 草稿 → 编辑 → 提交 → 审核 → 已审核 → 作废 → 已作废 → 反作废 → 已审核。
4. **已审核不可直接编辑**：所有字段（单号、日期、物料、数量、金额、自定义字段、明细增删、明细单元格、操作列删除）全部置灰。
5. **作废严格校验**：销售订单下已经生成了销售出库单 → 点【作废】→ 提示"存在下游单据，请先作废：销售出库单 XXX"并阻止。
6. **终态完结检查**：
   - 已结案：【编辑】【保存】【提交】【审核】【反审批】【删除】【作废】全部禁用/隐藏，仅【反结案】可见。
   - 已作废：同上所有操作不可用，仅【反作废】可见。
7. **批处理**：列表选 10 条包含已审核/草稿/已结案混合 → 点【批量结案】→ 展示"成功 X 条，失败 Y 条（单据 Y1：已结案不可重复结案；单据 Y2：草稿不能结案…）"。
