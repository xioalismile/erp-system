# 分支与版本管理说明

## 一、总原则

1. `main` 永远保持"能跑、能交付"的状态。
2. 改动按批次开分支，合并完就删，不长期积累。
3. 每次交付、每次上线打标签；标签永不删除、永不移动。

## 二、什么时候开分支

| 情况 | 做法 |
|---|---|
| 改文案、改一个字段、小修补 | 直接在 `main` 上提交 |
| 新功能、跨多个文件、要做几天 | `feature/功能名` |
| 修线上问题 | `fix/问题名`，修完立刻合并并打标签 |
| 一次性客户定制 | `custom/客户简称-需求`，交付后合并，打交付标签 |
| 长期并存的客户定制 | `custom/客户简称`，长期分支，定期合并 `main` |
| 试一个不确定的方案 | 随便开，做不成直接删掉 |

判断标准只有一条：**这次改动做完之前，`main` 能不能继续正常用？** 不能，就开分支。

## 三、命名规则

- 功能：`feature/批次追溯`
- 修复：`fix/单据号跳号`
- 客户定制：`custom/客户简称-需求`
- 标签：`baseline-日期`（基线）、`deliver-客户-日期`（交付）、`release-版本号`（上线）

名字用中文没关系，能看懂最重要。

## 四、日常操作

```powershell
git switch -c feature/批次追溯     # 开分支
git add -A                          # 暂存改动
git commit -m "feat: 批次追溯"       # 提交
git switch main                     # 切回主干
git merge feature/批次追溯           # 合并
git branch -d feature/批次追溯       # 删除短分支
git tag deliver-客户-20261127        # 打标签
git push                            # 推送主干
git push origin deliver-客户-20261127 # 推送标签
```

## 五、客户定制的三条规矩

1. **优先做配置开关，不改代码**。能做开关的定制，将来给别的客户复用成本几乎为零；改代码的定制，每个客户一套分支，越拖越难维护。
2. **长期定制分支要定期合并 `main`**，建议每周一次，否则三个月后合并全是冲突。
3. **交付必须打标签**。分支可以删，标签不能删——以后要找回"当时交给客户的那一版"，靠的是标签。

## 六、讨论新功能或客户定制时，先确认四件事

每次开始讨论方案前，先明确：

1. 这次是**新功能 / 修问题 / 客户定制 / 通用优化**？
2. 要不要开分支？分支名是什么？
3. 会不会影响已交付的客户？需不需要单独分支或配置开关？
4. 做完后要不要打交付标签、标签叫什么？

小修不必强推分支；涉及新功能、跨模块改动、客户定制时，这四问必须先过一遍。

## 七、配合仓库之后，bug 测试的建议

有了版本控制，测试的重点从"全都重测一遍"转向"只测这次动到的范围"，具体变化：

1. **先建分支再修**。`fix/问题名`，修完对比 `git diff main`，一眼看清这次到底动了哪些文件，回归范围就按这个清单来，不用凭记忆猜。
2. **每个修复必须带验证方法**。在提交说明或缺陷台账里写清楚：页面路径 → 操作步骤 → 预期结果。下次再出同类问题，照着重现即可。
3. **合并前只跑受影响范围 + 一轮冒烟**。用 `git diff --stat main` 判断影响面；跨了通用组件（列表页、编辑页、状态机）才扩大到相关模块。
4. **测试记录绑定标签**。写清楚"本次验证基于 `deliver-客户-20261127`"，以后出问题能确定是哪一版。
5. **用 `git bisect` 定位引入问题的版本**。发现以前正常、现在不正常时，不用翻聊天记录，让 git 二分查找哪次提交引入的。
6. **缺陷台账跟代码一起版本化**。建议 `docs/缺陷记录.md`，一条一行：编号、现象、复现步骤、修复提交号、验证结论。跟着仓库走，不会丢。
7. **测试数据和测试单据不进仓库**。用脚本生成种子数据（`tests/` 下），换台电脑也能一键重建同样的测试环境。
8. **提交前自检**：前端 lint、后端编译、关键页面冒烟——这三样通过再合并，比事后发现更省时间。

一句话：**以前测试靠"全量手点"，现在测试靠"改动范围 + 标签基线 + 可重复的复现步骤"。**

## 八、提交说明怎么写

前缀 + 一句业务描述：

- `feat: 委外发料审核即扣库存`
- `fix: 单据号保存后跳号`
- `docs: 补充批次规则说明`
- `refactor: 统一状态机审批入口`

一行说清"改了什么业务行为"，不写技术细节堆砌。
