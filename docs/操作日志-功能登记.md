### 3. 字段级改前/改后"时序缺陷"修复（2026-08-16）

- **验收（当时）**：改物料 MAT000001 名称 → `sys_operate_log_detail` 正确记录 `测试物料A → 测试物料A-已修改`

### 5. 恢复"改前/改后"（2026-09-15）★

- **现象**：改单位名称两次，`sys_operate_log` 有 2 条「修改」记录，但点开**看不到改前/改后**
- **根因（实证）**：08-16 的 `captureOldSnapshot` 修复**未留在源码**——磁盘源码停在 07-30 版（含 `valuesEqual` 但没有快照），
  `tryBuildFieldChanges()` 又回到 `proceed()` 之后的 finally 里读旧值，时序缺陷原样复现。
  旁证：`发布包/1.0.5/smart-erp.jar`（2026-08-16 08:22 打包）反编译**含** `captureOldSnapshot`/`OldSnapshot`，当前源码/`target/classes` 均无。
- **修复**：按 1.0.5 发布包实现原样恢复 `captureOldSnapshot()` + `OldSnapshot` +
  `recordLog(..., OldSnapshot)`；`aroundWrite()` 在 `proceed()` 前抓快照
- **附带修复**：`SysOperateLogServiceImpl.getByBill()` 原先**无排序**（最旧在前），
  而弹窗会自动展开第 1 条 → 用户看到的永远是最旧那条（多为无明细的早期记录）。
  改为 `SortHelper.orderByNewest(wrapper, SysOperateLog.class)`（最新在前）
- **实测证据**：改 `U004` 单位名称两次 → logId 140 `个1→个1-验证A`、141 `个1-验证A→个1`；
  弹窗数据链路返回顺序 `[141,140,…]`，自动展开的第 1 条含 1 行明细；前端点击级验证控制台报错 0
- **影响文件**：`backend/.../config/BillOperateLogAspect.java`、`backend/.../system/service/SysOperateLogServiceImpl.java`
  （**无 SQL / 无新接口 / 无新权限 / 不改前端**）

### 6. 三个"审计质量缺陷"修复（2026-09-15）

均只改 `BillOperateLogAspect.java`，实测证据见下。

| # | 缺陷 | 根因 | 修复 | 实测 |
|---|------|------|------|------|
| 1 | 销售订单等出现「客户名称/销售员名称/币种编码：空 → 值」**假变更行** | 这些是 `@TableField(exist=false)` 展示字段，库里没值，旧值恒空、新值恒来自请求体 | `diffObjects` 跳过 `exist=false` 字段 | 改备注后明细仅 `备注`；修复后新写 3 条日志 0 假行（旧历史记录保留不改） |
| 2 | 删除日志「单据编号」记的是**主键 ID**（如 `删除 物料 101`） | DELETE 请求体里没有实体，取不到编码 | 新增 `loadEntityById()`，DELETE 在 `proceed()` 前按 id 读实体，用其编码当单据编号 | 删除单位 → `bill_no = ZZ-E2E-…`（编码），不再是 `42` |
| 3 | `bill_type` 可能**串台**（`/api/purchase/orders` 被记成「销售订单」） | `URL_BILL_TYPE_MAP` 用 `Map.ofEntries`，迭代顺序由 JVM 哈希盐决定、每次启动随机 | 新增 `URL_BILL_TYPE_KEYS`（key 按长度降序），**最长键优先**匹配 | `PUT /api/purchase/orders/3` → `bill_type = 采购订单` |

### 7. 「失败的操作被记成成功」修复（2026-09-15）★

- **缺陷**：`operate_result` 恒为「成功」——`recordLog` 拿到了 `error` 参数却从未使用；
  被业务拒绝的操作（必填项未填 / 409 编码已存在 / 404 记录不存在 / 抛异常）在日志里也显示成功，
  并且照样写了**未生效的变更明细**（"日志说改了、实际没改"），审计上是误导。
- **修复**：
  1. `SysOperateLogService.saveBillLog` 12 参 → 14 参（新增 `operateResult`、`failReason`），
     唯一 12 参调用点 `BillOperateLogAspect.recordLog` 同步；8 参便捷版保留并委托（`BillActionTool` 在用）。
  2. 切面新增 `judgeResult(result, error)`，**两种失败形态都覆盖**：
     ① 抛异常（服务层校验失败 → 全局异常处理器）② Controller 正常返回但 `Result.code != 200`（409/404/业务 500）。
  3. **失败时不写字段级明细**（明细语义 = 实际发生的变更）。
  4. 前端可见：`LogList.vue` 操作结果列在失败时 hover 出 `fail_reason`；
     `ChangeRecordDialog.vue` 显示红色「失败」标签 + 失败原因块。
- **实测证据**：

| 场景 | 响应 | 日志结果 |
|------|------|---------|
| 销售订单缺"交货日期" | `code:500` | logId 148 `失败` / `failReason=【销售订单】请填写必填项：交货日期` / 明细 **0** 行 |
| 新增单位用已存在编码 | `code:409` | logId 149 `失败` / `编码已存在` / 明细 0 |
| 删除不存在的单位 | `code:404` | logId 150 `失败` / `记录不存在` / 明细 0 |
| 采购订单正常改备注 | `code:200` | logId 151 `成功` / 明细 2 行 |

前端点击级：销售订单页 →「操作日志」→ `修改 失败 lyc123` + `失败原因：…交货日期`，明细 0 行；
设置中心 → 日志 → 操作日志 → 失败行 hover tooltip = `记录不存在`；**控制台报错 0 / HTTP≥400 = 0**。

**影响文件**：`config/BillOperateLogAspect.java`、`system/service/SysOperateLogService.java`、
`system/service/SysOperateLogServiceImpl.java`、`views/system/LogList.vue`、`components/ChangeRecordDialog.vue`
（**无 SQL / 无新接口 / 无新权限**）
