# 系统性能优化 - 功能登记

> 本文件登记"页面加载慢"类问题的**已查明原因、已做优化、待办优化**。
> 每次再做性能相关改动，先读本文件，避免重复踩坑。

---

## 一、已完成（2026-09-15）

### 1. 每个 API 请求重复跑鉴权查询 → 加缓存（已上线）

**现象**：打开任意单据页要 2~4 秒（本地 127.0.0.1，数据量很小）。

**根因**：`AuthInterceptor.preHandle` 对**每一个** `/api/**` 请求都重跑一遍：

| SQL | 来源 |
|---|---|
| `sys_user_role WHERE user_id=?` | loadUserRoleIds |
| `sys_role WHERE role_id IN (?)` | loadRoleCodes |
| `sys_user WHERE user_id=?` | loadEmployeeId |
| `sys_user WHERE user_id=?` | loadDeptId ← **与上一条同一行，纯重复** |
| `sys_role_permission` ×2 | loadUserPermissions |

**处置**（`backend/.../config/AuthInterceptor.java`）：
- 合并 `loadEmployeeId` + `loadDeptId` 为一次 `selectById`（去掉 1 条重复查询）
- 鉴权上下文加 **30 秒内存缓存**（key = userId，`ConcurrentHashMap`）
- 到期自动失效；权限/角色/用户变更处主动 `evict`：
  - `SysRoleServiceImpl`：saveRole / updateRole / deleteRole / assignPermissions / assignButtonPermissions → `evictAll()`
  - `SysUserServiceImpl`：updateUser / deleteUser / assignRoles → `evict(userId)`

**实测**：5 个顺序请求期间，鉴权查询从**每请求 5 条**降到**仅第 1 个请求有、其余 0 条**；
`sys_user` 从每次 2 条降到 1 条。

> **安全红线**：缓存 key 必须按 userId 隔离；JWT 解析/401/403 逻辑未改动。

### 2. localhost 走 IPv6 回退，每次建连白等 ~70ms（已上线）

**现象**：单个 347 字节的接口也要 ~100ms。

**根因**（实测 TCP 阶段数据）：
```
端口 3000 (vite) 监听：0.0.0.0   ← 只有 IPv4
localhost 解析：      ::1 (IPv6) 优先
connect: 74 / 66 ms            ← 先试 ::1 失败，再回退 127.0.0.1 的代价
ttfb:    39 / 18 ms            ← 服务端其实很快
```
**Chrome 每次新建连接都要付这 ~70ms**，一个页面十几个请求就是好几秒。

**处置**（`frontend/vite.config.js`）：`server.host` 由 `'0.0.0.0'` 改为 `'::'`（Node 在 Windows 上默认双栈，IPv4-mapped 仍可访问）。

**实测**：

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| connect | 74 / 66 ms | **2 / 1 ms** |
| ttfb | 39 / 18 ms | 15 / 15 ms |
| 单请求总计 | 115 / 85 ms | **20 / 21 ms** |

- 3000 端口监听从 `0.0.0.0` → `::`；`127.0.0.1:3000` 与 `[::1]:3000` 均返回 200 ✓
- 页面各接口耗时**整体腰斩**：470→263、444→231、421→223、410→218、378→243、363→228、360→201

### 3. 星号工具重复请求字段权限（已上线）

`utils/fieldRequiredMark.js` 原先直连 `getCurrentUserFieldPermission`，而页面自己也会调
`useFieldPermission(pageKey)` → 同一 pageKey 发两次。
已改为复用 `loadFieldPermission(pageKey)`（模块级缓存 + 在飞请求去重）。

**实测**：`/api/role-field-permission/current/page/sale_order` 出现次数 2 → **1**，重复请求归零。

## 二、已排除（不是这些原因，不要重复查）

| 曾被怀疑 | 实测结论 |
|---|---|

## 三、待办（已量化，尚未做）

打开一个销售订单页的实测构成：

| 项 | 实测值 | 性质 |
|---|---|---|
| 前端模块请求 | **107 个** | **vite 开发模式独有，打包后消失** |
| API 请求 | **34 个**（无重复） | 真实开销 |
| domContentLoaded / loadEvent | 160 / 166 ms | 正常 |
| 页面彻底安静 | **~3 秒** | 受上面两项制约 |

**候选优化方向**（按性价比排序，做之前先给方案）：

1. **减少页面打开的 API 请求数**：34 个里大部分是"每个下拉一个 list 接口"
   （customer/material/employee/currency/payment-term/price-level/unit/warehouse/location/bank-account）
   → 可合并为一个批量接口，预计能砍掉 10 个左右请求。
2. **`/api/system/i18n/package/zh-CN`（58KB，408ms）**：内容按版本静态，可加长缓存。
3. **`/api/sys-config/group/*` 多次调用**（ui / notification / menu_name / approval.enabled / public/basic）：
   可合并为一次返回。
4. **Hikari `maximum-pool-size: 10`**：并发高时可上调，但需压测后定，不要盲改。

> 生产环境（打包 dist + 反向代理）不会有那 107 个模块请求，实际体验会明显好于本地开发模式。

## 四、踩坑记录

1. **PowerShell 传 `-Dmaven.test.skip=true` 必须加引号**，否则报 `Unknown lifecycle phase ".test.skip=true"`。
2. **agent-browser 的 `@e5` 这样的 ref 必须加引号**（`'@e5'`），否则被 PowerShell 当数组语法吞掉。
3. **agent-browser 的 `eval` 不能直接传带双引号的 JS**，PowerShell 会吃掉内层引号
   → 把 JS 写成文件，再 `[Convert]::ToBase64String` 后用 `eval -b` 传。
4. **`Get-Content -Raw` 读 UTF-8 中文文件要带 `-Encoding UTF8`**，否则按 GBK 解码会产生假 MISS。
5. **同一文件在同一批里做多个 SearchReplace 会静默丢改动**（读-改-写互相覆盖，工具仍回报成功）
   → 同文件多处修改必须串行，改完用读盘复核。
6. **判断"慢在哪"不能靠猜**：先用 `performance.getEntriesByType('resource')` 拆
   `connect / ttfb / download` 三段，才能区分"建连慢 / 服务端慢 / 传输慢"。
